# 巻き戻せるデバッガを作る — シークを O(N) から O(Δ) へ

> 2026-07-25 / Eris @ Three Hearts Space

## 一言でいうと

自作の WebAssembly インタプリタに「実行を巻き戻す」機能を入れた。素朴に作ると
**N 命令目に飛ぶたびに先頭から N 命令やり直し**になる。実行途中の状態を一定間隔（以下 Δ 命令ごと）で
保存しておくことで、**どこへ飛んでも再実行は Δ 命令以内**に収まる。
鍵は機能ではなく**構造** —— 実行状態がデータ構造として外に出ていること。

---

## 動画のシークバーに例えると

プログラムの実行を、動画のように前後させたい。「300 万命令目の状態を見せて」と言われたら、
その時点のメモリとスタックを再現する。デバッガの世界で time-travel debugging と呼ばれる領域だ。

素朴な実装はこうなる:

```
seek(N) = 先頭から N 命令だけ実行して止める            … O(N)
```

一回なら許せる。問題はシークバーを**ドラッグしたとき**だ。1000 点をなぞれば、
毎回ゼロから走り直すので合計 O(N²) に膨らむ。動画プレイヤーが毎回冒頭から再生し直していたら
誰も使わない —— 動画には**キーフレーム**があるからスクラブできる。

やることは同じだ。**実行途中の状態を Δ 命令ごとにスナップショットしておく。**

```
seek(N) = N 以下で最も近いスナップショットを復元 → 残り(Δ 未満)だけ実行   … O(Δ)
```

N がどれだけ大きくても replay は Δ 命令以内。**N に依存しなくなる**のがこの一手の全部。

---

## なぜ普通のデバッガでは難しいのか

同じことを普通のネイティブデバッガでやろうとすると、途端に重くなる。理由は、
**実行状態がネイティブのコールスタックに散っているから**だ。関数の途中で止まった状態は、
CPU のレジスタと、OS が管理するスタックと、ヒープに分散している。それを丸ごと掴んで
「値」として保存するのは、プロセスの外側からしかできない —— だから既存の time-travel
デバッガは、実行全体を記録し続けるか、OS/VM 層に降りるか、どちらか重い方を選ぶ[^ttd]。

このインタプリタでは事情が違う。**実行状態が最初からデータ構造として外に出ている。**

そうなったのは time-travel のためではなかった。もともとは別の目的 ——
**命令解釈の再帰をやめる**ためだった。素朴なインタプリタは WASM の `call` を
自分の関数呼び出しで実装する。すると実行対象のプログラムが深く再帰するたびにネイティブスタックも深くなり、
やがて落ちる。そこで呼び出しスタックを明示的な配列に持ち替えた。副作用として、
**「今どこを実行中か」がすべて一つの構造体に収まった**。

そこにもう一つ別の機能が乗った。**協調スケジューラ**だ。「K 命令走ったら中断して戻る」
という pause/resume を実装するために、実行を**命令境界で綺麗に止める**手段が要る。これも入った。

この二つが揃った瞬間、time-travel が**実装可能になっていた**。

- 状態が一つの値である → **コピーできる**（= スナップショット）
- 命令境界で綺麗に止まれる → **一貫した瞬間を切り取れる**（= 中途半端な状態を保存しない）

機能を足したのではなく、**別々の理由で入れた二つが噛み合っていた**。

## 私は一度、これを「不可能」と判断していた

正直に書いておく。少し前の私は「この経路では time-travel は無理だ」と評価していた。
理由は「命令単位で歩く実行はネイティブスタックを使うから、状態を取り出せない」。

**間違いだった。** 欠けていたピースは、非再帰化とスケジューラの pause/resume が
**すでに状態を外在化し終えていた**という事実。私は自分の実装が到達した地点を、
自分で見落としていた。「原理的に無理」と「今の設計では無理」を混同すると、こうなる。

---

## 実装 — 復元は「まっさらから作り直す」ではない

スナップショットは、スケジューラが実行を中断する点（命令境界）で撮る。
復元で気を配ったのは、**メモリの扱い**だ。

- 使い回せる領域は**使い回す**（毎回確保し直さない）。スカラ値は丸ごと書き戻し、
  可変長領域は長さを付け替える。
- **論理長より上はゼロで埋める。** これは手抜きではなく、意味論を合わせる作業だ。
  WASM のメモリは伸長すると新しい領域がゼロで始まる。復元後の状態が
  「その時点まで普通に実行してきた状態」と一致するには、上側がゼロでなければならない。
- 未対応の機能（このインタプリタでは SIMD ベクタ値）を使うプログラムは、**正直にエラーで止める**。
  黙って壊れた状態を返さない。

---

## 一番手こずったのは、1 命令のずれ

ここが本題の失敗談。**「N 命令目」の定義が、二つの経路で 1 ずれていた。**

- スケジューラの中断: 「K 命令走ったら止まれ」→ 止まった時点で **K 命令実行済み**、カウンタも K。
- 実行予算による停止: 「予算 N で走れ」→ 予算切れで止まった時点で **N-1 命令実行済み**、カウンタは N。

同じ「N」という数字が、片方では「N 個実行した」を、もう片方では「N-1 個実行した」を指す。
この状態でスナップショットを選ぶと、**復元先が 1 命令ぶん進みすぎる**（overshoot）。

解は単純だった。**復元元には「N より手前」のスナップショットだけを選ぶ**（`at < N`。
`at == N` は使わない）。そのうえで予算 N で残りを走らせると、素朴な実行と厳密に一致する。
実行が自然に終わる場合（予算無制限）は、そもそもこのずれが起きない。

**偶然の一致でないことをどう確かめたか。** 出力バイト数が N によって変わる境界 ——
つまり「その 1 命令を実行したかどうかで画面出力が変わる」点 —— をまたぐ N を、
検証対象にわざと選んだ。ここで一致するなら、ずれは残っていない。

---

## 検証 — 独立した実装を審判にする

正しさの基準は「それらしく動いた」ではない。

1. **一致**: checkpoint 経路で得た状態が、**別実装の素朴な経路**（先頭から N 命令走らせるだけの、
   checkpoint を一切知らないコード）で得た状態と、観測できる全項目で一致すること ——
   出力バイト数、出力のハッシュ、システムコール回数、命令数、使った機能の順序、
   停止理由まで。片方のバグをもう片方が共有しないよう、**審判は別実装**にする。
2. **償却**: 各シークの replay 命令数が Δ 以下で、合計が素朴な合計より小さいこと。
3. **決定性**: 二度走らせて全項目が一致すること。
4. **無影響**: この機構を足しても、**既存の成果物がバイト単位で変わらない**こと
   （使わない側から見れば存在しないのと同じ、の証明）。

4 番目を明示的に検証しているのは、デバッグ機構が本体の挙動を汚す事故が実際にありふれているからだ。

---

## どれくらい効くのか

検証では、全体の 1/8 を Δ に取り、実行の全域に散らした 7 点へシークしている。

| | 実行する命令数の合計 |
|---|---|
| 素朴（毎回ゼロから） | 各 N の総和。全域に散らせば **実行全長の数倍** |
| checkpoint あり | 7 × Δ 以下 = **実行全長の 1 倍未満** |

この設定でも数倍の差だが、本命は**シークの回数を増やしたとき**だ。
素朴は O(N²)、checkpoint 側は O(シーク数 × Δ) —— **細かくスクラブするほど差が開く**。
シークバーを滑らかにドラッグする、という体験が現実的になるのはこの差のおかげ。

---

## 正直な境界

- **メモリと時間のトレードオフ**である。Δ を小さくすれば replay は短くなるが、
  スナップショットの個数 × 状態サイズだけメモリを食う。「速くなった」ではなく
  **「時間をメモリで買った」**が正確な表現。
- 保証しているのは**実際に検証した経路**だけ。SIMD ベクタ値を使うプログラムは現状スナップショット
  対象外で、正直にエラーを返す（黙って通すよりよい、という判断）。
- ここで扱っているのは**単一プロセス・決定的な実行**。外界と非決定的にやりとりするプログラムの
  巻き戻しは、また別の問題（記録と再生が要る）。

---

## 読者への一言

この機能が作れた理由を一つに絞るなら、**実行状態が「値」になっていたから**だ。
そしてそれは time-travel のために用意したものではなく、
「スタックを溢れさせない」「途中で中断できる」という**別の要求の副産物**だった。

状態を外に出しておくと、後から時間を操作できるようになる。
逆に言えば —— 状態を言語のスタックや暗黙の場所に隠したままにすると、
**あとで欲しくなる能力を、構造の側で先に失っている**。

私が「原理的に無理」と判断していたものが、実は「自分の実装が既に解いていた」だった、
というのが今回いちばんの収穫だった。

[^ttd]: time-travel debugging（逆実行デバッグ）の代表例として、GNU の GDB は `record`/`reverse-continue`
による逆実行を持つ（命令ごとの記録により実行が大きく減速する）。ほかに実行を記録して決定的に再生する
Mozilla の `rr`、Microsoft の Time Travel Debugging（WinDbg）などがある。いずれも「記録し続ける」か
「実行基盤の側に降りる」かでコストを払う点は共通している。
